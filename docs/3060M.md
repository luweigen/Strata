# Strata on an RTX 3060 Laptop GPU: a manual conda install, speed and BFCL against llama.cpp

This page records work on one desktop PC (RTX 3060 Laptop GPU 12 GB on a desktop card, Ryzen 9 8945HX, 92 GiB
RAM; details in [The PC](#the-pc)), 2026-10-02/03:

- an install done by hand, without `setup.py`: the same steps setup does, with every dependency in an active conda
  environment (`strata`) instead of `.venv` and a system CUDA toolkit. Use it when you want Strata in your own conda
  environment, have no sudo, or already have the GGUF files;
- the GSQ-RCO Coder IQ1_M and Unsloth's UD-IQ4_XS (not a setup choice) measured against llama.cpp on a Strix Halo,
  on the tasks of EngramHalo.cpp's `docs/strix-halo/windows.md`;
- `/v1/completions`, added to the server for BFCL's path B, and BFCL multi-turn pilots against the Strix Halo's
  llama.cpp runs;
- where the CPU time goes during BFCL (threads, SMT, temperatures).

## Why not setup.py

`./setup.sh` was tried first. Two things made the manual route the better one on this PC:

- **No ready-made engine.** Step 4 got HTTP 404 for the release download (v0.1.34, then the latest release), so the
  engine has to be compiled here.
- **The CUDA toolkit needs sudo.** setup installs `cuda-toolkit-13-0` through apt (`setup.py` `install_build_tools`),
  which asks for a password and stopped the run: `sudo: a terminal is required to read the password`.
- **Its Python packages go into `.venv`,** not into the conda environment. `setup.sh` creates `.venv` from whatever
  `python3` is first on PATH (here the conda one), with `include-system-site-packages = false`.

The CUDA toolkit from conda needs no sudo and lives in the environment, so everything below goes there. The `.venv`
setup made was deleted afterwards.

## 2. Python packages

The same pinned packages setup installs, into the active environment:

```sh
conda activate strata
python -m pip install -r requirements.txt
```

This includes `cmake` 4.4.3 and `ninja` 1.13.2, used for the build.

## 3. The CUDA toolkit, from conda

```sh
conda install -n strata -c nvidia/label/cuda-13.0.3 -c nvidia cuda-toolkit=13.0.3
```

Installed: `cuda-toolkit` 13.0.3, `cuda-nvcc` 13.0.88, `cuda-cudart` 13.0.96, `libcublas` 13.1.1.3. `nvcc` is in
`$CONDA_PREFIX/bin`, the libraries in `$CONDA_PREFIX/lib`. CUDA 13.0 is what setup installs; an RTX 30 card (sm_86)
would also build with 12.x.

## 4. The engine

llama.cpp at the pinned commit (`3cf0325`) is in `third_party/llama.cpp` (the first `setup.py` run downloaded it;
`setup.py` `get_llama_cpp` shows the zip URL). The build uses setup's CMake flags, plus `CUDAToolkit_ROOT` so CMake
finds the conda toolkit:

```sh
cmake -G Ninja -S . -B build -DCMAKE_BUILD_TYPE=Release \
      -DSTRATA_ENABLE_CUDA=ON -DSTRATA_BUILD_TESTS=OFF -DCMAKE_CUDA_ARCHITECTURES=86 \
      -DCMAKE_CUDA_COMPILER=$CONDA_PREFIX/bin/nvcc -DCUDAToolkit_ROOT=$CONDA_PREFIX \
      -DSTRATA_GGML_DIR=$PWD/third_party/llama.cpp
cmake --build build --target strata -j 16
mkdir -p engine && cp build/strata engine/strata
```

It built on the first attempt (126 steps, system gcc 13.3.0 as the host compiler). `ldd engine/strata` shows
`libcudart.so.13`, `libcublas.so.13` and `libcublasLt.so.13` from `~/miniconda3/envs/strata/lib`.

`engine/BUILD.json` is written as setup writes it for a local build (`"source": "local"`, `"archs": [86]`, the
source fingerprint from `setup.source_hash`, `cuda_dirs` = the environment's `bin` and `lib`), so a later
`setup.py` sees the engine as already built.

## 5. The pack

The model data go to `../Strata-data`, setup's default data folder, so setup finds them too. The experts stay in the
GGUF and are read from it at start; the pack holds the index, the dense tensors and the tokenizer:

```sh
export STRATA_GGUF_PY=$PWD/third_party/llama.cpp/gguf-py
python tools/iq_pack.py \
  --gguf ~/Documents/Qwen3.8-Flash-Next-GSQ-RCO-Coder-GGUF/IQ1_M/Qwen3.8-Flash-Next-GSQ-RCO-IQ1_M-00001-of-00002.gguf \
  --out ../Strata-data/packs/coder-iq1_m
```

Result: 1079 tensors, 302 served natively, arena 1.37 GiB; `tokenizer/` with a vocabulary of 248320. The low-RAM
`--experts-bin` file is not needed: IQ1_M uses ~23 GB of RAM and this PC has 92.

## 6. The MTP draft layer

The draft layer for speculative decoding comes from the original Qwen checkpoint (only its MTP tensors, 4.9 GB):

```sh
M=../Strata-data/mtp
python tools/mtp_fetch.py fetch --out $M
python tools/mtp_pack.py --src $M --experts q2_0 --out $M/mtp-q2_0.gguf
python tools/mtp_rt.py --gguf $M/mtp-q2_0.gguf --out $M/rt
cp data/draft_vocab.bin $M/rt/draft_vocab.bin     # setup's default subset (cjk)
```

## Against llama.cpp on Strix Halo (the same tasks)

EngramHalo.cpp's `docs/strix-halo/windows.md` ("Expert-pruned GSQ-RCO Coder vs IQ4_XS", 2026-10-01) measured this
same model file, the GSQ-RCO Coder, with its llama.cpp branch on an AMD Ryzen AI MAX+ 395 (Radeon 8060S iGPU, 128 GB
LPDDR5X, 96 GB carved for the GPU, Windows 11). The same tasks were run here with Strata on 2026-10-02.

**How it was run here.** One server start, nothing else on the GPU, the config above (32K context, 8-bit KV,
MTP draft layer with `--spec 4`), temperature 0, numbers from the `timings` object of `/v1/chat/completions`. The
script is `benchmarks/2026-10-02-3060m-bench_halo.py`, its raw results
`benchmarks/2026-10-02-3060m-coder-iq1_m.json`; its prompts:

- server sequence, 400 tokens out each: a rewrite of `llama_get_list_splits` (cold first request), a rewrite of
  `select_weight_buft` (fresh prompt), the first 4749 tokens of `llama-model-loader.cpp` + "summarize it function
  by function", then the first prompt again
- llama-bench shape: 4085 tokens of EngramHalo's other `src/llama-*.cpp` files (pp, 1 token out); "write a
  thread-safe LRU cache" (tg, 128 tokens out); at depth, a 16384-token prefix of the same sources, then the prefix
  + 4037 more tokens

**Server sequence:**

| | Strix Halo, llama.cpp (windows.md) | RTX 3060 Laptop, Strata (this PC) |
|---|---|---|
| model load to listening | 30 s | 11.5 s (19 s the first start after the copy) |
| cold first request, decode (MTP) | 26.1 t/s, 86.5% acc | **43.3 t/s**, 88.1% acc |
| fresh code prompt, decode (MTP) | 21.9 t/s, 74.5% acc | **42.1 t/s**, 80.0% acc |
| prefill @ ~4.75K | 321.5 t/s (4754 tokens) | **961.3 t/s** (4749 tokens) |
| decode tail after that prefill | 20.8 t/s, 81.9% acc | **39.3 t/s**, 77.5% acc |
| repeated prompt (reference only) | 49.9 t/s | 45.1 t/s, 91.7% acc |

**llama-bench shape:**

| test | Strix Halo, llama-bench | RTX 3060 Laptop, Strata server |
|---|---|---|
| pp4096 @ d0 | 318.1 +/- 70.0 (warm-up pass 365.3) | **926.9** (4085 tokens) |
| tg128 @ d0 | 20.92 +/- 0.19 (plain decode) | 36.2 (MTP, 61.4% acc) |
| pp4096 @ d16384 | 269.9 +/- 1.2 | **~1126** (derived, see below); 1084.6 over the whole 20421-token prompt |
| tg128 @ d16384 | 17.98 +/- 0.15 (plain decode) | 37.4 (MTP, 65.3% acc) |

**What differs, read before comparing:**

- **Different machines, not only different engines.** Strix Halo keeps the whole model in GPU-visible memory
  (LPDDR5X shared with the iGPU). Here the GPU holds 2666 of the experts (5.11 GiB of its 12 GB) and the
  CPU computes the rest from RAM; an RTX 3060 has much more compute for prefill than the 8060S.
- **tg is MTP here, plain decode there.** Strata's server does not run without the MTP draft layer (`strata serve:
  needs --spec T, --mtp DIR and --prefill CHUNK`), so llama-bench's plain `tg128` has no direct counterpart. The
  server-sequence rows are the like-for-like decode comparison: both sides use MTP there (llama.cpp with the EasiiX
  MTP sidecar + `draft-mtp,ngram-mod`, Strata with its own draft layer).
- **pp4096 @ d16384 is derived.** The chat cache did not reuse the 16384-token prefix (`cache_n` 0: it keeps whole
  turns, and the second prompt is one longer user turn), so that request prefilled all 20421 tokens. The rate of
  the last 4037 tokens is the difference of the two requests: (20421 - 16384) tokens / (18.83 s - 15.24 s) = 1126
  t/s. llama-bench prefills only the 4096 at depth.
- **Chat API vs raw completion.** Strata has only `/v1/chat/completions` and `/v1/messages`, so every prompt went
  through the chat template and the model thought before answering; windows.md used llama.cpp's `/completion`.
  windows.md does not record its exact prompts: the prompts here are of the same kind (a function rewrite, a
  4.75K chunk of `llama-model-loader.cpp`), not the same text.
- **Context:** 32K here, 163840 there. **KV:** 8-bit on both.
- Every request here stopped at its `max_tokens` (`finish: length`). n=1 per row, one session.

**Reading it:** on this PC Strata decodes this model at about 2x the Halo llama.cpp speed (39-43 t/s vs 21-26 t/s
with MTP on both) and prefills about 3x (961 vs 321 t/s at 4.75K). The MTP acceptance is in the same range on both
(78-88%). The repeated-prompt row is the one where llama.cpp is ahead (49.9 vs 45.1 t/s): its ngram speculator
reuses the answer it has seen, and Strata's suffix drafting does not seem to gain as much there. Quality was not
compared.

## Unsloth UD-IQ4_XS (not a setup choice): it runs

Unsloth's UD-IQ4_XS of the original model (3 shards, 93.7 GB) is not one of setup's sizes; setup offers only
UD-Q4_K_XL of Unsloth's files. It was tried by hand on 2026-10-02, the same way as the Coder above.

**The file.** Shard 1 holds metadata only (10.9 MB); shards 2 and 3 hold the tensors, and layer 14's gate, up and
down are split across them. The experts are IQ3_S (33.9 GB), IQ4_NL (20.3 GB), Q8_0 (4.5 GB) and IQ4_XS (0.9 GB):
55.4 GiB in all, which fits in this PC's 92 GB of RAM, so the engine keeps all of them there (not setup's
UD-Q4_K_XL mode, which keeps a RAM budget and reads the rest from the SSD). The `mtp-...-Q8_0.gguf` llama.cpp
sidecar in the same folder is not used: Strata uses its own draft layer (step 6, shared with the Coder).

**The pack** (29 s; with `--compat-bf16`, as setup does for UD-Q4_K_XL):


Result: every tensor accepted; `native_experts.txt` v4 (the per-role shard column for layer 14); 1079 tensors,

**The config** `strata-unsloth-ud-iq4_xs.json` is the Coder's with `--pack`, `--native` (shard 1),

## `/v1/completions` (added for BFCL's path B)

BFCL's path B renders the Qwen3 prompt itself and sends it to `/v1/completions`, which Strata did not have. It was
added to `serve/server.py` (tests: `serve/test_server.py`, class `Completions`; documented in DETAILS.md, "Using
it"):

- the prompt is one string (special tokens such as `<|im_start|>` read as tokens, as llama.cpp does) or one list of
  token ids; no chat template;
- the model's text comes back unparsed: `<think>` and `<tool_call>` stay in `text` (a pass-through parser in place
  of `OutputParser`; the queue, timings, history and engine restarts are the chat endpoint's);
- `stop` (a string or a list) ends the text before the first match; a stream holds back text that may be the start
  of one; `max_tokens` unset / 0 / -1 = the rest of the context, a prompt that does not fit is a 400;
- OpenAI's `text_completion` shape, streamed or not, with `usage` (`cached_tokens`) and llama.cpp's `timings`;
  `echo`, `suffix`, `logprobs` and `n`/`best_of` > 1 are refused with a 400.

On the engine (Coder IQ1_M): a raw Qwen prompt answered with `timings` (36.2 t/s, 15/15 drafts accepted); `stop:
["return"]` cut the text right before it; a prompt ending at `assistant\n` returned the model's own
`<think>...</think>` as text; the next request reused 17 cached prompt tokens.

## Where the CPU time goes during BFCL

The Ryzen 9 8945HX has 16 cores on two chiplets (CCD1: cores 0-7, CCD2: 8-15) and 32 threads: logical CPUs 16-31
are the SMT siblings of cores 0-15 (`lscpu -e`). The engine pins one expert-pool worker per physical core (15
workers on cores 1-15, `src/kernels/cpu/pool.cpp`) and its host thread on core 0, which spins to answer the GPU
without delay; the SMT siblings are left idle on purpose (`src/core/session.cpp`: another thread on a worker's core
or its sibling took the CPU path from 36.3 to 26.9 GB/s on the machine that was measured).

Measured over 5 s during the 400-item UD-IQ4_XS path B run (`/proc/stat`):

| | core 0 | cores 1-15 (expert workers) | SMT siblings 16-31 | clock |
|---|---|---|---|---|
| CCD1 (cores 0-7) | 100% (the host thread) | 12% each | 0-3% | 5083 MHz |
| CCD2 (cores 8-15) | | 12% each | 0% | 4901 MHz |

The GPU was at 100%. The workers are idle most of the time because a BFCL call is mostly prompt, and Strata reads
prompts on the GPU; the expert pool only works during the short decode. More threads (the 16 SMT siblings,
`--pool-workers 31`) would add workers to a pool that waits most of the time, and the CPU's expert path is limited by
memory bandwidth, which a sibling does not add. For long answers (decode-heavy work such as coding sessions) the
worker count can matter; `tools/calibrate.py` tries fewer workers than the default. Not measured on this PC.

Temperatures at the same time (`~/temp.sh`): CPU Tccd1 87.1 °C, Tccd2 63.1 °C, Tctl 85.0 °C; GPU 60 °C at 100%;
iGPU 57 °C; SSD 42.8 °C. CCD1 is warmer because it holds core 0 with the spinning host thread (seven engine threads are
pinned to CPU 0, the host thread among them), and it runs about 180 MHz faster than CCD2; the worker load is spread evenly over
both. 87 °C is below the 8945HX's 100 °C limit.
