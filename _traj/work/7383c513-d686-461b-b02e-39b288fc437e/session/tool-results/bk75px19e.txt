     1	# The patch set, and how it was audited
     2	
     3	*This is the record of an audit run against the predecessor repository, kept because it explains why
     4	the patch order is what it is and why five of these scripts were generated rather than written. The
     5	tooling it names now lives in `bootstrap/bootstrap.py`.*
     6	
     7	Audit of 2026-09-19, produced by `bootstrap/bootstrap.py --verify` and re-runnable at any
     8	time. This exists because the repository accumulated 47 patch scripts across two backends, of which
     9	only two were referenced from the manager or the scripts, and nothing recorded which ones produce the
    10	binary that runs. Everything below is measured from the tree and the running process, not read off
    11	documentation — one documentation claim turned out to be wrong (see IQ3_S).

    63	## The gap: 5 modified files no script owns
    64	
    65	`mmb.cu`, `mmb.cuh`, `softcap.cu`, `softcap.cuh`, `mmid.cu`.
    66	
    67	**`mmid.cu` is a comment only**: a note recording that a counting sort was tried in place of the
    68	bitonic expert sort and lost (906 against 946 t/s pp16384). No code change.
    69	
    70	**The other four are the IQ3_S MMB kernel and the sigmoid fusion, and they are live in production.**
    71	They exist only as whole-file copies in `patches/iq3s-kernel/`, with no `apply_*.py` script, so a
    72	clean rebuild from the patch scripts alone would silently omit the single largest measured win in
    73	the project: +4.8% prefill and +5.5% decode (pp16384 947.37 against 903.64, tg128 24.97 against
    74	23.66), from letting the 52.2% of the model body stored as IQ3_S reach the matrix cores.
    75	
    76	`patches/iq3s-kernel/README.md` states "It is not in production". That is wrong, on three
    77	independent pieces of evidence:
    78	
    79	1. The four files in that directory are byte-identical to the production tree.
    80	2. `mmb.cu:921` passes `allow_iq3s = true` from the fused-GLU caller, with no runtime gate.
    81	3. The running server logs `MMB_GLU fused gate/up+swiglu: ... type=IQ3_S`.
    82	
    83	### Settled 2026-09-19: the rollback reason is obsolete, keep the kernel
    84	
    85	The rollback was attributed by elimination, not root cause, and predates the real fix. On 2026-09-18
    86	every "answer stops mid-sentence" report was traced to speculative verification batches running dense
    87	attention with no causal mask, fixed by `apply_qsa_small_batch_mask.py`, which is live.
    88	
    89	Re-measured on the current build. `STRIX_MMB_IQ3S=0` was added to `mmb.cu` so both arms are the
    90	same binary with one variable; `tools/truncation_test.py --fill 70000 --reps 1`, fresh server per
    91	arm, verified by `type=IQ3_S` appearing in one server log and not the other:
    92	
    93	| | 68499-token prefill | answer | sections |
    94	| --- | --- | --- | --- |
    95	| IQ3_S on | **876.7 t/s** | 1110 tokens, `finish_reason=stop` | **30/30** |
    96	| IQ3_S off | 830.6 t/s | 1085 tokens, `finish_reason=stop` | **30/30** |
    97	
    98	Both reach 30/30: the truncation is gone. Prefill is **+5.6%**, matching the +4.8% originally
    99	claimed. The kernel stays, and `STRIX_MMB_IQ3S=0` stays as the switch to reach for when a future
   100	numerics or long-generation regression has to be attributed.
   101	
   102	(The decode rates in that test are not a comparison - it is a speculative run and the two arms drew
   103	different draft counts.)

   105	## The deeper gap: the scripts cannot rebuild the tree on their own
   106	
   107	`ggml-cuda.cu` also carries unscripted content, and the counts line up exactly with the snapshot in
   108	`patches/iq3s-kernel/`, not with anything the live scripts insert:
   109	
   110	| marker in `ggml-cuda.cu` | production tree | all 17 live scripts | iq3s snapshot |
   111	| --- | --- | --- | --- |
   112	| `GGML_UNARY_OP_SIGMOID` | 11 | 0 | 11 |
   113	| `scale_sigmoid` | 2 | 0 | 2 |
   114	| `NO_SIGMOID_FUSE` | 2 | 0 | 2 |
   115	| `LLAMA_GRAPH_DUMP` | 3 | 0 | 3 |
   116	| `GT compute` | 1 | 0 | 1 |
   117	| `mmb_supported_mmid` | 3 | 0 | 3 |
   118	
   119	So the production tree is **snapshot first, scripts second** - the 17 scripts layer onto
   120	`patches/iq3s-kernel/`, not onto clean upstream. `GT compute` is the `LLAMA_GRAPH_TIMING` line the
   121	whole decode-budget analysis is built on, and it exists only in that snapshot.
   122	
   123	A bootstrap therefore has three steps, and this order is not optional:
   124	
   125	1. check out `pwilkin/llama.cpp` at `f5daaa3...`;
   126	2. overlay the six files in `patches/iq3s-kernel/` (whole files, hash-verifiable);
   127	3. apply the 17 live scripts, respecting the ordering table above.

   160	### The audit that got here (kept for the reasoning)
   161	
   162	`tools/replay_bootstrap.py` does exactly that and is re-runnable. Only 20 files differ from
   163	upstream, so only those are restored: normally out of the clone's own git objects, addressed by the
   164	blob hash in `bootstrap/UPSTREAM.json`, or with `--fetch` through a mirror and checked against the
   165	recorded SHA-256 — all 20 verified either way. The reconstructed tree then matches upstream in every recorded file,
   166	the snapshot goes on, the scripts run in the order above, and every delta file is compared.
   167	
   168	    clean-upstream check: ok
   169	    patches   : 15 applied, 2 failed
   170	    REPRODUCED 17 / 24
   171	
   172	So most of the build is now provably reproducible, and the seven that are not each have a named
   173	cause. None of them is guesswork:
   174	
   175	| File(s) | Why it does not reproduce |
   176	| --- | --- |
   177	| `ggml-cuda.cu` | `STRIX_NODE_TIMING`, the per-dispatch HIP event instrumentation, is in **no script and not in the snapshot** — an unrecorded edit straight into the tree |
   178	| `mmid.cu` | comment-only note about a rejected counting sort; unrecorded, harmless, fold into the snapshot |
   179	| `vecdotq.cuh` | `apply_iq3s_vecdot_hip` is stale: its `OLD_LOOP` anchor occurs in neither upstream nor the production tree, so the script can no longer produce what the tree contains |
   180	| `models/qwen4exp.cpp` | the PLE prefetch half (`launch_prefetch` / detached thread) has no working script; `apply_hip_ple_probe` reports "already applied" and writes nothing |
   181	| `llama-model.cpp`, `llama-model.h`, `llama-graph.cpp` | `apply_trunk_decode_twins` fails with "anchor not unique" against clean upstream — written against an already-modified tree |
