   520	## `/v1/completions` (added for BFCL's path B)
   521	
   522	BFCL's path B renders the Qwen3 prompt itself and sends it to `/v1/completions`, which Strata did not have. It was
   523	added to `serve/server.py` (tests: `serve/test_server.py`, class `Completions`; documented in DETAILS.md, "Using
   524	it"):
   525	
   526	- the prompt is one string (special tokens such as `<|im_start|>` read as tokens, as llama.cpp does) or one list of
   527	  token ids; no chat template;
   528	- the model's text comes back unparsed: `<think>` and `<tool_call>` stay in `text` (a pass-through parser in place
   529	  of `OutputParser`; the queue, timings, history and engine restarts are the chat endpoint's);
   530	- `stop` (a string or a list) ends the text before the first match; a stream holds back text that may be the start
   531	  of one; `max_tokens` unset / 0 / -1 = the rest of the context, a prompt that does not fit is a 400;
   532	- OpenAI's `text_completion` shape, streamed or not, with `usage` (`cached_tokens`) and llama.cpp's `timings`;
   533	  `echo`, `suffix`, `logprobs` and `n`/`best_of` > 1 are refused with a 400.
   534	
   535	On the engine (Coder IQ1_M): a raw Qwen prompt answered with `timings` (36.2 t/s, 15/15 drafts accepted); `stop:
   536	["return"]` cut the text right before it; a prompt ending at `assistant\n` returned the model's own
   537	`<think>...</think>` as text; the next request reused 17 cached prompt tokens.

   733	## Where the CPU time goes during BFCL
   734	
   735	The Ryzen 9 8945HX has 16 cores on two chiplets (CCD1: cores 0-7, CCD2: 8-15) and 32 threads: logical CPUs 16-31
   736	are the SMT siblings of cores 0-15 (`lscpu -e`). The engine pins one expert-pool worker per physical core (15
   737	workers on cores 1-15, `src/kernels/cpu/pool.cpp`) and its host thread on core 0, which spins to answer the GPU
   738	without delay; the SMT siblings are left idle on purpose (`src/core/session.cpp`: another thread on a worker's core
   739	or its sibling took the CPU path from 36.3 to 26.9 GB/s on the machine that was measured).
   740

   759	## `--pcie-frac`: decode and prefill
   760	
   761	`--pcie-frac` is the share of the experts the GPU does not hold that are copied to the GPU over PCIe for each token;
   762	the CPU computes the rest from RAM. Without the flag the engine measures the link at start and keeps its default when
   763	the link is fast: here "PCIe probe: 26.8 GB/s host->device -> pcie_frac 0.55 (default 0.55)" (`src/program/generate.cpp`:
   764	20 GB/s or more keeps the default). The rule does not compare the link with the CPU's own path to RAM, and on this PC
   765	the two are far apart: the PCIe link moves 26.8 GB/s (measured), the CPU reads RAM at about 55 GB/s (measured above),
   766	and the copies are read from the same RAM, so they take their 26.8 GB/s out of the ~55 the CPU workers share.
   767	
   768	**The prediction** (from these bandwidths): decode is best near 0.2 for the Coder and 0.25 for UD-IQ4_XS; prefill
   769	the other way, 0.65-0.85.

   824	### Why the engine picks 0.55 here, and a draft of a better default
   825	
   826	**The rule** (`src/program/generate.cpp`, the `pcie_frac < 0` block; the same rule again for a layer split's other
   827	cards): native packs start from 0.55, "measured on x16 links (~26-28 GB/s)"; the engine probes the link at start and
   828	keeps 0.55 from 20 GB/s up, scales it down below that (`0.55 x link / 26`), and uses 0 below 4 GB/s. The code also
   829	records the machine it was measured on: 6 cores, the pool kernel reading 44.14 GB/s, the pool draining 33.7 GB/s
   830	(`no_host_worker`'s comment, `include/strata/kernels/cpu/pool.hpp`). This PC has the same kind of link (26.8 GB/s),
   831	but its CPU side is very different: 15 workers instead of 5, two chiplets, about 55 GB/s of RAM read. The rule
   832	only looks at the link, so it keeps a value measured for a different CPU. `tools/calibrate.py` measures the share
   833	per PC (0, 0.2, 0.35, 0.55, 0.75, keeping the fastest) and would have found 0 or 0.2 here; setup offers it after an
   834	install, but not with `--yes`, and this install did not go through setup.
   835	
   836	**A sentence in DETAILS.md that this PC contradicts.** DETAILS.md ("For byte-identical repeats ...") says:
   837	"`--pcie-frac 0` costs decode speed (the missed experts all run on the CPU), so keep it for A/B runs." Measured
   838	here, 0 is the fastest value or tied for it (Coder 65.1 t/s at 0, 62.3 at 0.2, 51.9 at 0.55; UD-IQ4_XS 55.4 at 0 and
   839	at 0.25, 44.6 at 0.55). The sentence holds on the machine the default was measured on, not in general; it should
   840	say so (for example "costs decode speed on PCs where the default share is right; run `--calibrate`"). DETAILS.md is
   841	not changed here.
   842	
   843	**A draft** (`src/program/generate.cpp`, 2026-10-04, compiled; not yet run in the engine - the GPU was busy):
   844	
   845	- `probe_host_read_gbps(threads)`: the host RAM read bandwidth with the pool's thread count (one per physical core),
   846	  a 1 GiB buffer, best of 3 passes; about 0.3 s at start, only when the share is not given.
   847	- `default_pcie_frac(native, link, host)`: one function for both places the rule was written. The link-only rule
   848	  is unchanged. With `STRATA_PCIE_HOST_RULE=1` it also weighs the link against the host:
   849	  `0.55 x (link / host) / (27 / 44.14)` - the measuring machine's link-to-kernel ratio - and never raises the value.
   850	- The probe line now also prints the host bandwidth: "PCIe probe: 26.8 GB/s host->device, host RAM read X GB/s ->
   851	  pcie_frac ...", so starts on other PCs collect both numbers.
   852	
   853	Tested on its own (the two functions compiled into a small program, 2026-10-04, while a BFCL run used the GPU and
   854	RAM): the probe read **45.0 GB/s** with 15 threads (55 GB/s idle with the STREAM test above); rule off: 0.55 / 0.28 /
   855	0 for a 26.8 / 13 / 2 GB/s link, as before; rule on: **0.54** at 26.8 GB/s and 45 GB/s, 0.44 with 55 GB/s, 0.55 for
   856	the measuring machine's numbers, 0.21 for a 13 GB/s link; the canonical pack keeps 0.2.
   857	
   858	**So the ratio is not the explanation.** Weighing the link against RAM bandwidth moves the share from 0.55 to
   859	0.44-0.54 on this PC; the measured best is 0-0.25. What the draft does not measure is what most likely differs:
   860	the pool's own expert throughput (15 workers here, 5 there; the IQ kernels may be limited by compute, not only by
   861	RAM) and the GPU's side of the copies (the copy kernel runs on the GPU's SMs: 30 on this GPU, 48 on an RTX 5070).
   862	That is why the rule stays opt-in. Next measurement, when the GPU is free: decode at `--pcie-frac` 0 and 0.55 with
   863	the engine's pool counters (`pool phases ... drain`) and the GPU's per-token times, to see which side waits. The
   864	alternatives to a formula: let setup run `--calibrate` also with `--yes`, or balance the share at run time from
   865	the measured drain and copy times (the share is already settable per request: `strata_tune` key `pcie_frac`).
