     1	# Strata on an RTX 3060 Laptop GPU: a manual conda install, speed and BFCL against llama.cpp
     2	
     3	This page records work on one desktop PC (RTX 3060 Laptop GPU 12 GB on a desktop card, Ryzen 9 8945HX, 92 GiB
     4	RAM; details in [The PC](#the-pc)), 2026-10-02/03:
     5	
     6	- an install done by hand, without `setup.py`: the same steps setup does, with every dependency in an active conda
     7	  environment (`strata`) instead of `.venv` and a system CUDA toolkit. Use it when you want Strata in your own conda
     8	  environment, have no sudo, or already have the GGUF files;
     9	- the GSQ-RCO Coder IQ1_M and Unsloth's UD-IQ4_XS (not a setup choice) measured against llama.cpp on a Strix Halo,
    10	  on the tasks of EngramHalo.cpp's `docs/strix-halo/windows.md`;
    11	- `/v1/completions`, added to the server for BFCL's path B, and BFCL multi-turn pilots against the Strix Halo's
    12	  llama.cpp runs;
    13	- where the CPU time goes during BFCL (threads, SMT, temperatures).
    14	
    15	## The PC
    16	
    17	A desktop mini board, not a laptop: a mobile CPU (Ryzen 9 8945HX) on a mini-ITX-class board, and a mobile GPU chip
    18	(GA106M, "RTX 3060 Laptop GPU") on a desktop PCIe card, the kind sold as a converted laptop GPU (subsystem ID
    19	`10de:0000`, no OEM's). The model's experts live in system RAM; the GPU holds the dense layers, the KV cache and a
    20	cache of experts (2666 of the Coder's, 1864 of UD-IQ4_XS's); the experts it does not hold are computed by the CPU
    21	from RAM or copied to the GPU over PCIe (`--pcie-frac`). So the numbers that matter are the GPU's VRAM and memory
    22	bandwidth, the PCIe link, the RAM's bandwidth and the CPU's cores. Read on 2026-10-03 with `lscpu`, `nvidia-smi -q`,
    23	sysfs and `lspci`; "spec" marks a vendor figure, "measured" one measured on this PC.

    85	- **Read, what Strata's expert workers do** (they only read weights): about **55 GB/s** with 15-16 threads, 66% of
    86	  the 83.2 GB/s theory; at most 57.0 with 4 threads on each chiplet. One thread already reaches 46 GB/s and 2-4
    87	  reach 51: memory, not the number of cores, is the limit.
    88	- **One chiplet** reads 46-50 GB/s, both together 55-57: each chiplet's Infinity Fabric link nearly fills the memory
    89	  on its own, so spreading over both adds about 10%.
    90	- **SMT siblings add nothing** (55.3 with 32 threads vs 55.5 with 16; memset drops from 54.5 to 49.3), which agrees
    91	  with Strata leaving them idle.
    92	- **Plain stores count half**: `write` and the stores in `copy`/`triad` first read each cache line
    93	  (read-for-ownership), so 24 GB/s counted is about 48 GB/s of real traffic. Non-temporal stores (glibc's
    94	  memset/memcpy at this size) skip that: 54-65 GB/s for writing.
    95	- For comparison on this PC: the GPU's VRAM 336 GB/s (spec), the PCIe link 26.8 GB/s measured. The experts the GPU
    96	  does not hold are read by the CPU at most at about 55 GB/s, or copied to the GPU at 26.8 GB/s.

   154	- **No FP32-output penalty here**: FP32 out runs at 96-97% of 16-bit out on the engine's shape (28.0 vs 29.0),
   155	  where the Halo's hipBLAS loses 5-6x. Every `cublasGemmEx` the engine issues asks for FP32 out, so this card needs
   156	  no tuning table for it.
   157	- **The library is near the card's limit**: GeForce Ampere does FP16/BF16 with FP32 accumulate at 512 operations
   158	  per clock per SM (from NVIDIA's RTX 3090 figure: 71 TFLOPS, 82 SMs, 1695 MHz), 30.4 TFLOP/s for 30 SMs at
   159	  1980 MHz. 28-29 TFLOP/s is 92-95% of that. FP16 accumulate is twice the rate (60.8); 37-39 TFLOP/s measured,
   160	  and the Halo branch found FP16 accumulate too inexact for the engine (1.2e-2 relative error against 3.3e-4).
   161	- **The small shapes take 47-51 us each** whatever their size: the expert gate/up (1.05 GFLOP) 22 TFLOP/s, the
   162	  down (0.52 GFLOP) 10.6, decode-like (0.10 GFLOP) 2.0. The decode-like call reads 12.6 MB of weights in 50 us,
   163	  252 GB/s, 75% of the VRAM's 336 GB/s.

   165	  22 TFLOP/s, but the engine's experts stay quantized for MMQ, which reads each 0.5-1.7 MB expert once instead of a
   166	  dequantized FP16 copy.

   186	## Why not setup.py
   187	
   188	`./setup.sh` was tried first. Two things made the manual route the better one on this PC:
   189	
   190	- **No ready-made engine.** Step 4 got HTTP 404 for the release download (v0.1.34, then the latest release), so the
   191	  engine has to be compiled here.
   192	- **The CUDA toolkit needs sudo.** setup installs `cuda-toolkit-13-0` through apt (`setup.py` `install_build_tools`),
   193	  which asks for a password and stopped the run: `sudo: a terminal is required to read the password`.
   194	- **Its Python packages go into `.venv`,** not into the conda environment. `setup.sh` creates `.venv` from whatever
   195	  `python3` is first on PATH (here the conda one), with `include-system-site-packages = false`.
   196	
   197	The CUDA toolkit from conda needs no sudo and lives in the environment, so everything below goes there. The `.venv`
   198	setup made was deleted afterwards.

   243	## 4. The engine
   244	
   245	llama.cpp at the pinned commit (`3cf0325`) is in `third_party/llama.cpp` (the first `setup.py` run downloaded it;
   246	`setup.py` `get_llama_cpp` shows the zip URL). The build uses setup's CMake flags, plus `CUDAToolkit_ROOT` so CMake
   247	finds the conda toolkit:
   248	
   249	```sh
   250	cmake -G Ninja -S . -B build -DCMAKE_BUILD_TYPE=Release \
   251	      -DSTRATA_ENABLE_CUDA=ON -DSTRATA_BUILD_TESTS=OFF -DCMAKE_CUDA_ARCHITECTURES=86 \
   252	      -DCMAKE_CUDA_COMPILER=$CONDA_PREFIX/bin/nvcc -DCUDAToolkit_ROOT=$CONDA_PREFIX \
   253	      -DSTRATA_GGML_DIR=$PWD/third_party/llama.cpp
   254	cmake --build build --target strata -j 16
   255	mkdir -p engine && cp build/strata engine/strata
   256	```
   257	
   258	It built on the first attempt (126 steps, system gcc 13.3.0 as the host compiler). `ldd engine/strata` shows
   259	`libcudart.so.13`, `libcublas.so.13` and `libcublasLt.so.13` from `~/miniconda3/envs/strata/lib`.
   260	
   261	`engine/BUILD.json` is written as setup writes it for a local build (`"source": "local"`, `"archs": [86]`, the
   262	source fingerprint from `setup.source_hash`, `cuda_dirs` = the environment's `bin` and `lib`), so a later
   263	`setup.py` sees the engine as already built.

   265	## 5. The pack
   266	
   267	The model data go to `../Strata-data`, setup's default data folder, so setup finds them too. The experts stay in the
   268	GGUF and are read from it at start; the pack holds the index, the dense tensors and the tokenizer:
   269	
   270	```sh
   271	export STRATA_GGUF_PY=$PWD/third_party/llama.cpp/gguf-py
   272	python tools/iq_pack.py \
   273	  --gguf ~/Documents/Qwen3.8-Flash-Next-GSQ-RCO-Coder-GGUF/IQ1_M/Qwen3.8-Flash-Next-GSQ-RCO-IQ1_M-00001-of-00002.gguf \
   274	  --out ../Strata-data/packs/coder-iq1_m
   275	```
   276	
   277	Result: 1079 tensors, 302 served natively, arena 1.37 GiB; `tokenizer/` with a vocabulary of 248320. The low-RAM

   370	## Against llama.cpp on Strix Halo (the same tasks)
   371	
   372	EngramHalo.cpp's `docs/strix-halo/windows.md` ("Expert-pruned GSQ-RCO Coder vs IQ4_XS", 2026-10-01) measured this
   373	same model file, the GSQ-RCO Coder, with its llama.cpp branch on an AMD Ryzen AI MAX+ 395 (Radeon 8060S iGPU, 128 GB
   374	LPDDR5X, 96 GB carved for the GPU, Windows 11). The same tasks were run here with Strata on 2026-10-02.
   375	
   376	**How it was run here.** One server start, nothing else on the GPU, the config above (32K context, 8-bit KV,
   377	MTP draft layer with `--spec 4`), temperature 0, numbers from the `timings` object of `/v1/chat/completions`. The
   378	script is `benchmarks/2026-10-02-3060m-bench_halo.py`, its raw results
   379	`benchmarks/2026-10-02-3060m-coder-iq1_m.json`; its prompts:
   380	
   381	- server sequence, 400 tokens out each: a rewrite of `llama_get_list_splits` (cold first request), a rewrite of
   382	  `select_weight_buft` (fresh prompt), the first 4749 tokens of `llama-model-loader.cpp` + "summarize it function
   383	  by function", then the first prompt again
   384	- llama-bench shape: 4085 tokens of EngramHalo's other `src/llama-*.cpp` files (pp, 1 token out); "write a
   385	  thread-safe LRU cache" (tg, 128 tokens out); at depth, a 16384-token prefix of the same sources, then the prefix
   386	  + 4037 more tokens
   387	
   388	**Server sequence:**
   389	
   390	| | Strix Halo, llama.cpp (windows.md) | RTX 3060 Laptop, Strata (this PC) |
   391	|---|---|---|
   392	| model load to listening | 30 s | 11.5 s (19 s the first start after the copy) |
   393	| cold first request, decode (MTP) | 26.1 t/s, 86.5% acc | **43.3 t/s**, 88.1% acc |
   394	| fresh code prompt, decode (MTP) | 21.9 t/s, 74.5% acc | **42.1 t/s**, 80.0% acc |
   395	| prefill @ ~4.75K | 321.5 t/s (4754 tokens) | **961.3 t/s** (4749 tokens) |
   396	| decode tail after that prefill | 20.8 t/s, 81.9% acc | **39.3 t/s**, 77.5% acc |
   397	| repeated prompt (reference only) | 49.9 t/s | 45.1 t/s, 91.7% acc |
   398	
   399	**llama-bench shape:**
   400	
   401	| test | Strix Halo, llama-bench | RTX 3060 Laptop, Strata server |
   402	|---|---|---|
   403	| pp4096 @ d0 | 318.1 +/- 70.0 (warm-up pass 365.3) | **926.9** (4085 tokens) |
   404	| tg128 @ d0 | 20.92 +/- 0.19 (plain decode) | 36.2 (MTP, 61.4% acc) |
   405	| pp4096 @ d16384 | 269.9 +/- 1.2 | **~1126** (derived, see below); 1084.6 over the whole 20421-token prompt |
   406	| tg128 @ d16384 | 17.98 +/- 0.15 (plain decode) | 37.4 (MTP, 65.3% acc) |
   407	
   408	**What differs, read before comparing:**
   409	
   410	- **Different machines, not only different engines.** Strix Halo keeps the whole model in GPU-visible memory
   411	  (LPDDR5X shared with the iGPU). Here the GPU holds 2666 of the experts (5.11 GiB of its 12 GB) and the
   412	  CPU computes the rest from RAM; an RTX 3060 has much more compute for prefill than the 8060S.
   413	- **tg is MTP here, plain decode there.** Strata's server does not run without the MTP draft layer (`strata serve:
   414	  needs --spec T, --mtp DIR and --prefill CHUNK`), so llama-bench's plain `tg128` has no direct counterpart. The
   415	  server-sequence rows are the like-for-like decode comparison: both sides use MTP there (llama.cpp with the EasiiX
   416	  MTP sidecar + `draft-mtp,ngram-mod`, Strata with its own draft layer).
   417	- **pp4096 @ d16384 is derived.** The chat cache did not reuse the 16384-token prefix (`cache_n` 0: it keeps whole
   418	  turns, and the second prompt is one longer user turn), so that request prefilled all 20421 tokens. The rate of
   419	  the last 4037 tokens is the difference of the two requests: (20421 - 16384) tokens / (18.83 s - 15.24 s) = 1126
   420	  t/s. llama-bench prefills only the 4096 at depth.
   421	- **Chat API vs raw completion.** Strata has only `/v1/chat/completions` and `/v1/messages`, so every prompt went
   422	  through the chat template and the model thought before answering; windows.md used llama.cpp's `/completion`.
   423	  windows.md does not record its exact prompts: the prompts here are of the same kind (a function rewrite, a
   424	  4.75K chunk of `llama-model-loader.cpp`), not the same text.
   425	- **Context:** 32K here, 163840 there. **KV:** 8-bit on both.
   426	- Every request here stopped at its `max_tokens` (`finish: length`). n=1 per row, one session.
   427	
   428	**Reading it:** on this PC Strata decodes this model at about 2x the Halo llama.cpp speed (39-43 t/s vs 21-26 t/s
   429	with MTP on both) and prefills about 3x (961 vs 321 t/s at 4.75K). The MTP acceptance is in the same range on both
   430	(78-88%). The repeated-prompt row is the one where llama.cpp is ahead (49.9 vs 45.1 t/s): its ngram speculator
   431	reuses the answer it has seen, and Strata's suffix drafting does not seem to gain as much there. Quality was not
   432	compared.
